# aion.adk.server

Aion server-side Google ADK integration — implements `AgentPluginProtocol` for the Aion Server runtime.

## Overview

This subpackage provides the server-side plugin for running Google ADK agents within the Aion platform. It handles:

- **Plugin & Adapter** — `ADKPlugin` / `ADKAdapter` implementing `AgentPluginProtocol` / `AgentAdapter`
- **Execution** — `ADKExecutor` / `ADKStreamExecutor`, running the agent through ADK's own `Runner`
- **Session management** — Memory and PostgreSQL backends via `SessionServiceFactory`
- **Artifact storage** — Memory and A2A-backed artifact service via `ArtifactServiceFactory`
- **Transformers** — Bidirectional A2A ↔ ADK format conversion

An agent's `path` in `aion.yaml` names an ADK agent (a `BaseAgent` instance) or a callable that returns one. The callable may be an `async def`: the server awaits it once at startup, on its own event loop, so a factory can load MCP tools or open a connection while it builds the agent.

## How an agent runs

The server runs an agent the way any ADK application does: through ADK's `Runner` (`Runner.run_async`). The Runner picks the agent that answers a message, resumes a paused invocation, writes the user's message and the agent's events to the session, and drives the agent; the server repeats none of that logic, so an agent behaves here as ADK documents it.

The Runner works only with what the server gives it (`execution/runner.py`):

- **Sessions** are the server's session service, memory or PostgreSQL. Every write, the Runner's included, passes one point where the turn in progress decides what a session keeps (`TurnSessionService`), and where a file an event carries inline is stored and kept as a link (see [Files in the session](#files-in-the-session)).
- **Artifacts** are the server's artifact service.
- **Nothing else is passed**: no memory service, no credential service, no plugins, no context cache, no event compaction. The Runner creates no session on its own; the server finds or creates it first.
- **The run configuration is fixed**: text out, streamed (`RUN_CONFIG`), and every invocation resumable.
- **The invocation context** is `AionInvocationContext`, which carries the Aion runtime context of the request.

After `transfer_to_agent` the next message of the context goes to the agent that answered last, as long as that agent may hand the conversation back to its parent (`disallow_transfer_to_parent` is off for it and for every agent above it); otherwise the root agent answers. That is the Runner's rule, unchanged.

## Inbound and outbound

The inbound A2A message becomes the invocation's `user_content`, part by part and in order: text as text, inline bytes as `inline_data` and a URL as `file_data`, each with its media type, and a structured data part as a text part holding its JSON. The part's metadata is not passed on.

On a deployment that stores files, a file is `file_data` with the file's address, and that is what the session keeps. A model is sent the content: `aion_lite_llm` replaces every part that carries a file by its `http(s)` address with `inline_data` in each request, and an agent with a model of its own sets `before_model_callback=inline_files_before_model` (`aion.adk.authoring.files`). The address is that of the deployment's storage, which works only with its authorization, so a provider cannot fetch it. A turn reads each file once, and the files of one model request at once: what a turn reads and stores is kept for the turn and goes with it (`aion.core.a2a.file_contents`), and the files its request brought are not downloaded back. A later turn reads a file from storage again, for as long as the file is kept. Every file of the request is sent on every call. A file goes with its own media type; which types a model takes is for the model service and the provider to decide, and the SDK keeps no list of its own. The event with a file stays in the session, so a file the model does not take would fail every later request too. `aion_lite_llm` leaves such a file out (`aion.core.agent.left_out_files`): a request the model refuses on what it carries - status 400, 413, 415 or 422 from the model service - Aion's model service answers with HTTP 200 and a stream, and names the provider's status at the start of the stream's `api_error` event - or a part `LiteLlm` cannot convert - is made again without one file, the newest first, and when no single file explains the refusal, each file is checked alone in a short request, streamed whatever the call is: the service answers only with a stream. A text note takes the place of each file the model refused, `[File "clip.mp4" (video/mp4) was not accepted by the model and was left out]` - for a tool's media, right after the function response - and later requests to the same model leave it out from the start, for as long as the server runs; a warning in the log names the file and the model. ADK and its callbacks see one model call, the one that went through; the session keeps the events as they were. A refusal no file explains, and any other failure, fails the call as before, and the error, left uncaught, fails the task with a reason that says the agent stopped on an unexpected error; `on_model_error_callback` may answer instead. An agent with a model of its own sees the refusal as its model's error: its `on_model_error_callback` notes the file, and a `before_model_callback` after `inline_files_before_model` leaves it out of later requests. A file larger than `AION_MODEL_FILE_MAX_BYTES` (default 20 MiB) is not read: a note says so in its place, `inline_files_before_model` included. A file the storage does not make available to the turn's sender - in a conversation several people share, one another participant stored - is not read either: `[File "a.pdf" (application/pdf) is not available to this sender and was left out]` takes its place, and the turn goes on. A file that is no longer stored is not read either: the SDK stores the files of a conversation for 30 days from their upload, and once the retention deadline its reference records has passed, or the storage says the file no longer exists, `[File "report.pdf" (application/pdf) is no longer available and was left out]` takes its place, and the turn goes on; a warning in the log names the file once a turn. Any other file that cannot be read fails the task and says so. A message may name a file by any address, so a file is downloaded from public addresses only, every redirect included: a host that resolves to a private, loopback, link-local or other non-public address is refused, and the connection goes to the address that was checked (`aion.core.http.file_transport`). The Aion API host (`AION_API_HOST`) is always allowed; `AION_FILE_TRUSTED_HOSTS` lists other hosts, comma-separated, that an agent is meant to reach on an internal address. These downloads take no proxy from the environment. With `aion_lite_llm` every file travels in the body of the request. ADK's `LiteLlm` puts an image, audio, video or text file there itself; any other document it would upload to the provider's Files API on every request when the model is OpenAI's, so `aion_lite_llm` hands it a text mark instead and its client puts the document into the finished request in the mark's place - Aion's model service is not a provider's Files API, and a document sent with the request leaves no copy behind. A request that lost a mark is not sent: the task fails and names the file. With a model class of the agent's own, how the content travels after `inline_files_before_model` is that class's.

What the model says reaches the client as it says it: partial events stream as deltas, and the non-partial event that closes a model call is the reply. Function calls, function responses and thoughts are not sent, and neither is code the model ran — `executable_code` and `code_execution_result` parts are left out of a reply. An agent that wants the client to see them sends them explicitly, as an artifact (`tool_context.save_artifact`), where they arrive as a data part. ADK's `Runner` writes every event the agent yields to the session before the agent resumes, so the next model call is built from a session that already holds the function response it follows.

A session belongs to one agent and one user: it is keyed `app_name` = the Aion agent id, `user_id` = the owner the agent's `owner_resolver` names for the request's `ServerCallContext` - by default its trusted user, and always the tasks table's `owner_scope`, `session_id` = the A2A `context_id`. Two users, or two agents on one database, presenting the same `context_id` get two sessions; memory between turns stays with its owner. Sessions saved before this key - under the agent's display name and the shared `default-user` - cannot be attributed to a user: a turn on such a context fails with `LegacyStateError`, and the old session is left in place until it is migrated or removed. The artifact service's fallback to the tasks table reads with the same agent and owner.

An agent has two ways to produce an artifact, side by side. `emit_artifact` (and `thread.post(artifact)`) publishes an A2A artifact as it is, as the LangGraph adapter does: every part, the artifact's own metadata, chunks of one artifact with `append`, and the `metadata` argument on the update event. It does not go through ADK's artifact service. ADK's own way, `tool_context.save_artifact`, keeps working as ADK documents it. The artifact service reads the context's task artifacts by name - through the tasks table with a database, through the turn's conversation history without one - so ADK's `load_artifacts` finds a published artifact too, as its first part: the one `Part` an ADK artifact holds; the whole artifact is in `aion.core.agent.conversation.find_artifact`. The latest version of a name is the newest one written in the current turn, saved or published, and before that the newest one the tasks hold. The artifact service holds what a turn writes in memory only until the turn ends: the turn's task holds it from then on, and a file in it is read through its link like any stored file. A `user:` artifact, which other sessions find in memory alone, stays there until five minutes after its last write. A version number asked for by name is ADK's own numbering of `save_artifact`; a published artifact carries the number SDK artifacts carry, if any, and several artifacts with different ids may share a name.

An artifact the agent saves (`tool_context.save_artifact`) is numbered per agent, user, context and name, from 0, and the number reaches the client as the artifact's `metadata.version`. With PostgreSQL, every number is recorded in `adk_artifact_versions` as it is given, so the servers of an agent never give one number twice: a save whose number another server took meanwhile numbers again from what the database holds, and fails with `ArtifactVersionConflictError` after ten such tries. Deleting the context removes the recorded numbers with its tasks.

A task has one streamed answer at a time, so agents that stream at once - the sub-agents of a `ParallelAgent` - take turns; a stream is told by its events' author and branch. The agent that started first streams live; the events of the others are held, and each follows as a section of its own once the one before it has ended, in the order they started. Every answer reaches the client whole. The task keeps the section that ended last, as it does after model calls made one after another: that is the agent that *started* last, whichever finished first. A `ParallelAgent` whose sub-agents each stream an answer should be followed by an agent that gives the turn's answer. A thought, a reaction or an artifact published as it is goes out at once, and so does the whole answer of an agent that does not stream, as a message beside the open section.

An event the agent yields keeps the author, branch and invocation ADK gave it: ADK shows a model another author's words as quoted data rather than as its own, and leaves another branch's events out. An event with no author or invocation - an agent written by hand may leave them empty - is given the turn's. Only events the SDK emits for the agent - through `Thread` or the `emit_*` helpers - are stamped as the agent's the Runner started the turn with: the root agent, or the sub-agent that took the conversation over on an earlier turn.

`a2a_outbox` answers the run that wrote it: the executor takes it from the run's own state deltas, and the value the session keeps afterwards is not applied to later turns of the same context.

### Files in the session

With a file storage backend configured, a session never holds a file's bytes. An event can carry a file inline - `inline_data` in its content, written by the agent, a callback, a model or `thread.post`, or a tool's media in its function response (`FunctionResponse.parts`), where ADK 2.7 and later put an image or a document a tool returns - and the session service would save it for as long as the session lives. `TurnSessionService` gives the session service a copy of the event with each such file stored and replaced by `file_data` holding the file's address, with the same media type and name; the files of an `a2a_outbox` in the event's state delta are kept as addresses the same way. The copy names the stored file behind each address in its `custom_metadata` (`aion:files`), which the session keeps and a model is never sent. A file the turn also sends to the client is stored once: the task and the session name the same stored file, whichever of the two asks first. Content the turn read from a stored file - a tool that returns the bytes of a file of the conversation - is not stored again: the session links that stored file, with its own reference and retention, unless the turn read several stored files with the same bytes (`aion.server.files.turn`). The running invocation is not affected: the event the Runner hands on is not changed, and the invocation's own session goes on with the event's content, so a model later in the same invocation is sent the bytes whatever its model class. A later turn reads the session as stored, with addresses: `aion_lite_llm`, or an agent's `before_model_callback=inline_files_before_model`, sends the model the content of every linked file, a tool's media as `inline_data` of its function response - the one form in which ADK's `LiteLlm` sends a tool's media at all - and reads a file by the stored file the session names, through a link issued for the turn. Inline data that carries an A2A data part is not a file and stays as it is. A file that cannot be stored fails the task, and the session is not written with the bytes instead. Without a file storage backend, the session keeps the bytes.

Before ADK 2.7 a tool has no media: a `Part` it returns is a value of its function response like any other result. The session keeps that value as it is, bytes included, and a model gets it inside the tool's result rather than as an image. ADK's `MultimodalToolResultsPlugin` adds the image to the one model call right after the tool, and does not change what the session keeps.

## Asking the user

Every invocation is resumable, as in an ADK `App` with `ResumabilityConfig(is_resumable=True)`. A run that makes a long-running tool call stops there, and the task waits in `INPUT_REQUIRED`: `request_input` (`google.adk.tools`), `tool_context.request_confirmation`, a `LongRunningFunctionTool`, or a custom agent's own long-running call. To a client this looks the way a LangGraph `interrupt()` does - one text part asking the question, and the call's id as the message's `interruptId`. The question is the `message` of `request_input`, the confirmation's `hint`, or "Agent requires input" for a call that names none.

The user answers with an ordinary message, and the server turns it into the function response the call waits for: a structured data part is the response as it is, a JSON object in the text is the response, and other JSON or plain text is `{"result": ...}`. A confirmation is ADK's `ToolConfirmation`, and the server judges no answer on the agent's behalf: a reply that is that object - a data part, or text holding it as JSON, such as `{"confirmed": true}` - is the response as it is; anything else, a text or the data of a pressed card button, reaches the agent unconfirmed, as the confirmation's `payload` (`{"text": ...}` or `{"data": ...}`). A tool that asked with `tool_context.request_confirmation` runs again and reads the answer in `tool_context.tool_confirmation.payload`; a tool ADK confirms for itself (`require_confirmation=True`) is confirmed by the object, or by the agent's `before_tool_callback`, which runs before ADK checks the confirmation and may set `tool_context.tool_confirmation.confirmed` from the payload. Files sent with the answer follow the function response in the same message, as `file_data` or `inline_data` like the files of any message, so the model reads them together with the answer. The invocation the call belongs to runs on, resumed by ADK's `Runner`: by the root agent when the root agent started it, so a `SequentialAgent` or `LoopAgent` goes on from the sub-agent that asked and runs the ones after it; by the agent that made the call when the invocation started in a sub-agent.

A request for credentials (`tool_context.request_credential`) fails the task with a reason saying so: the server cannot take credentials yet.

With a file storage backend configured, an inline file part (`Part(raw=...)`, or a `data:` URL) anywhere in the outbox is stored and replaced with a URL part before the response is delivered, as every outbound file is; a file that cannot be stored fails the task. The session state keeps the outbox with the same links (see [Files in the session](#files-in-the-session)).

## Failing a task

An agent, tool or callback that raises ends the turn with the task `FAILED`, and the status message says why, the same on the stream, in the unary answer and in a later `tasks/get`. To give the caller a reason of your own, raise `aion.core.exceptions.TaskFailedError("...")`; its text is the message, as written. An SDK error that names something the deployment lacks, such as a daemon identity, gives its own sentence the same way. Any other exception is a crash: the task says the agent stopped on an unexpected error and names the task to look up in the log, and the exception's text stays in the log.

A model response that ends with an error fails the task as well. ADK's models do not raise for a response that was blocked, cut short by the token limit or malformed: the event carries an `error_code` and, when the model gave one, an `error_message`, alone or beside the text that arrived before it. The run goes to its end as it does under ADK's `Runner`, and the task then closes `FAILED` with that code and message as its reason. The text streamed before the error stays in the task as its `aion:stream-delta` artifact and is not its answer.

## Installation

```bash
pip install "aionto-sdk[adk-server]"
```

The extra brings Google ADK, the authoring toolkit (`aion.adk.authoring`) and the server. `aion.server` finds this plugin on its own; without the extra it is skipped, and the skip names the extra to install.
